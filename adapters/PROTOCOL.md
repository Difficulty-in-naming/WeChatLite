# Local adapter protocol

The relay starts one local child process. UTF-8 NDJSON is exchanged over stdin/stdout; diagnostics go to stderr. It cannot connect to another computer's WeChat. The release Windows implementation is `adapters/windows-rs` (`wechat-adapter.exe`), with no Python interpreter or Python modules at runtime.

Relay commands:

- `{"op":"configure","groups":["..."]}`: replace the selected forwarding groups at runtime. Startup selection is passed as a JSON array in `WECHAT_LITE_FORWARD_GROUPS`; omission means no group is selected.
- `{"op":"activate","group":"..."}`: authorize an explicitly opened local group for sending, publish its members and up to 40 recent messages. Live reading of other local groups does not require native sender authorization.
- `{"op":"record_refresh","group":"...","source_id":"wx:..."}`: durably reread one existing merged-forward source in a selected group as historical data. The relay queues legacy summaries on reconnect, independently of the 40-message warm window. This never activates native sending or repeats an outgoing message.
- `{"op":"send","message":{...}}`: submit a persisted message with a UUID, text, actual member IDs and verified local media paths. Step IDs must remain stable across confirmation checks.
- `{"op":"receipt","source_id":"...","group":"..."}`: the relay has durably imported the incoming message and attachments.
- `{"op":"recall","message":{...}}`: explicitly request recall of a confirmed outgoing message in a selected group. The persisted message contains its `id`, `group`, `timestamp`, `outgoing`, `status` and stable WeChat `source_id` / `source_ids`.
- `{"op":"recall_check","message":{...}}`: recover an already persisted recall attempt after reconnect. This command checks existing worker/database confirmation only and must never submit a previously unsubmitted native action.

Adapter events:

- `{"type":"status","ready":true,"text":"..."}`
- `{"type":"groups","groups":[{"id":"...","name":"...","count":0}]}`
- `{"type":"members","group":"...","members":[{"id":"...","name":"...","remark":"..."}]}`
- `{"type":"message","message":{id,group,sender,sender_id,text,media,mentions,timestamp,status,source_id,outgoing}}`, optionally including `quote`, `source_ids`, `recall_status` and `recall_error`.
- `{"type":"ack","id":"client UUID","status":"sent|failed|uncertain","source_id":"first WeChat source","source_ids":["all acknowledged WeChat parts"],"timestamp":1790000000000,"error":"..."}` (`timestamp` is optional)
- `{"type":"recall_ack","id":"original client message ID","status":"recalled|failed|uncertain","error":"..."}`
- `{"type":"warning","text":"..."}`

`timestamp` is Unix milliseconds. Incoming `source_id` must be stable and unique in the group. Media paths must be absolute local paths; the relay copies and hashes files into its own date folders before acknowledging. Member IDs are required for actual mentions. An uncertain send must never be retried automatically. Incoming messages remain in the adapter journal until the relay receipt; native echoes of client sends must be deduplicated.

A `sent` ACK with a valid confirmed source may supply the first native part's database `create_time * 1000`. The relay replaces enqueue time only for an integer timestamp between the enqueue second and the current time plus two seconds; a slightly future value is clamped to now. Missing, malformed, stale, unconfirmed or failed ACK times preserve the previous timestamp. This keeps the recall window tied to the actual send after a long queue without trusting arbitrary ACK times.

An optional `quote` is `{id,sender,text,unavailable}`. Clients submit only the source `id`; the relay resolves the same-group stored source and fills its sender/text, rejecting missing, cross-group or recalled sources. The relay supplies the verified local source locator to the adapter internally. The Windows adapter rereads that exact source and uses the independent `WeChatQuote.dll` to create a real native appmsg with direct `type=57`. Only confirmed same-group native text sources (`local_type=1`) are supported. Media sources and nested quote/card sources fail explicitly; no quoted-summary fallback is sent. The reply text remains a separate field rather than being concatenated with a snapshot. Queue acceptance is not success: the adapter rereads the new message and verifies its native type-57 title, reference server ID, actor/from fields and content before acknowledging. A successful recall invalidates references to that source with `unavailable=true` and cleared quote text.

For an own source the native source fields are `fromusr=self`, `tousr=group`, `chatusr=self`; for an incoming source they are `fromusr=group`, `tousr=self`, `chatusr=the shard's verified Name2Id actor`. Plain body text cannot supply identity. Reference `displayname` may be empty in real WeChat XML. XML line-ending normalization is handled during confirmation without changing the original source/reply bytes being sent. Quote source lookup, receipt fingerprints and native actions remain independent of the client's local reedit cache.

`GET /api/messages/{id}?group=<selected-group>` retrieves one stored source for locating a reference outside the client window. Bearer authentication and current group selection are required; a wrong-group or missing ID returns 404 and a recalled source returns 410. The client performs at most one history-page request for the surrounding context after this lookup and cannot revive a source recalled during the lookup. The recalled message's blue reedit action only restores a private local draft and never writes withdrawn content back to relay history or emits a send request.

`POST /api/messages/{id}/recall {}` begins recall in the relay and returns the message with `recall_status="pending"`. The adapter validates every native source before submitting any part, persists stable per-part request IDs and checks the existing receipt after a lost reply or restart. Only the current account's confirmed messages less than 180 seconds old can be submitted. The optional version-pinned `WeChatActions.dll` must already have observed a complete native record matching the selected group, current account, server ID, local ID and creation time. A missing record is a definite pre-submission failure; the adapter never reconstructs one from database fields. Worker success plus the matching database `sysmsg/revokemsg` is required before emitting `recalled`. Failed or uncertain outcomes keep the original content, never repeat the native action automatically, and publish their distinct recall state.

Groups, members and messages may carry `avatar`: a Base64 JPEG string without a `data:` prefix, at most 64 pixels on the longest side. Omission or an empty value means no locally available avatar. Clients retain a bounded avatar cache and use an initial as fallback. Avatars are read from the local WeChat database; no avatar URL is fetched.

Incoming merged-forward cards (`appmsg/type=19`) may carry `record:{title,items:[{id,sender,text,timestamp,media:[index,...]}],pending}`. Item media indices refer to the enclosing message's ordinary `media` array, using the existing group ownership and download permissions. Items retain source order; their sender names grant no group-member identity or native action authority. CDN locators and AES keys remain adapter-private. Text is imported while child media downloads are pending; the relay withholds the source receipt until `pending=false`, allowing the durable retry queue to complete the same card. Updates preserve the canonical message ID and reuse imported attachment IDs. The client opens a read-only detail view and closes it on recall or permission invalidation. Nested records are flattened in source order (maximum 6 layers, 200 items, 1 MiB XML). Opening a group upgrades legacy summary-only cards in its recent 40 messages; explicit history pages upgrade older cards without moving live cursors.

The Windows reader publishes the full group catalog only to the local relay process, while reading messages only for selected local groups. Group discovery refreshes every 60 seconds and never automatically selects a new group. A newly watched group starts at its current tail, while persisted cursors recover messages after a restart. Opening a selected group adds recent history without rewinding the live cursor. Durable receipts deduplicate live polling, history backfill and reconnect replay. Background download authorization follows the administrator's selected local groups, including groups never opened in either chat UI. Native sending remains granted only when an explicit `activate` or a valid `send` targets a selected group. Removing a group revokes both scopes; shutdown revokes download access and an empty selection forwards nothing.

The relay has two distinct Bearer identities. The existing `Config.token` is the local administrator secret: it is accepted only from the original loopback TCP peer, including for ordinary HTTP APIs and WebSocket upgrades. A non-loopback attempt with that secret returns 403. Forwarded-address headers cannot grant administrator access. An independent client key remains a client identity even when used from loopback and cannot call any local management or shutdown endpoint. Invalid, disabled or permanently revoked client keys return 401.

`GET /api/local/forwarding` returns `{groups:[...],selected:[...]}` and `POST /api/local/forwarding` accepts `{selected:[...]}` for the local configuration window. Only the loopback administrator can read the complete local group catalog or change the global forwarding selection. An independent client's effective groups are the intersection of its own group grants and the global selected set; granting a group to a client does not select it globally. Grant IDs must exist in the local catalog. Adding client-key storage preserves the previous global selection and existing messages.

Client management also requires the loopback administrator:

| Method and endpoint | Request and response |
| --- | --- |
| `GET /api/local/clients` | Returns `{clients:[{id,name,enabled,revoked,groups,can_send,can_download,created_at,updated_at,revision}]}`. No token or token hash is returned. |
| `POST /api/local/clients` | Accepts `{name,groups?,can_send?,can_download?,enabled?}` and returns `{client:{...},token:"..."}`. The generated token is shown only in this creation response. |
| `POST /api/local/clients/{id}` | Accepts partial updates to `name`, `enabled`, `groups`, `can_send` and `can_download`; returns `{client:{...}}`. A disabled key can be enabled again. |
| `POST /api/local/clients/{id}/revoke` | Permanently revokes the key and returns `{client:{...}}`; it cannot subsequently be enabled. Create a new key to replace it. |

A new client defaults to `enabled=true`, `groups=[]`, `can_send=false` and `can_download=false`. Names contain 1–64 display characters. At most 256 client records are retained. SQLite stores only a SHA-256 digest of each random key alongside its grants; the plaintext cannot be retrieved later. The runtime registry and permission revisions avoid database polling for authorization. The user-supplied message `client_id` is a display/deduplication field, not an authentication identity; queued send and recall ownership is recorded internally from the authenticated key and omitted from public messages.

Each protected endpoint requires a valid Bearer identity. The local administrator retains ordinary access to globally selected groups; independent keys additionally obey these capabilities:

| Endpoint | Required effective group / capability |
| --- | --- |
| `GET /health` | Public application/version information only. |
| `GET /api/status` | Valid identity; returns `authenticated_client:{id,name,admin}` and own `permissions:{groups,can_send,can_download}`. Only the administrator also receives `online_clients`, the number of distinct independent keys with an open WebSocket; multiple sockets for one key count once. |
| `GET /api/groups` | Returns only groups in the effective set. |
| `GET /api/groups/{id}/members` | Read access to the effective group. |
| `POST /api/groups/{id}/activate` | Read access to the effective group. Local history/media preparation does not grant the client permission to retrieve attachment bytes. |
| `GET /api/messages?group=...` | Read access to that effective group, including search and history pagination. |
| `GET /api/messages/{id}?group=...` | Read access to that effective group; the stored message must belong to the requested group. Missing/wrong-group sources return 404 and recalled sources return 410. |
| `POST /api/messages` | Effective group plus `can_send=true`; quoted sources and every attachment must belong to that same group. |
| `POST /api/messages/{id}/recall` | Effective group plus `can_send=true`, and the existing outgoing/confirmation/180-second rules. |
| `POST /api/media?group=...&name=...` | Effective group plus `can_send=true`; the owner group is mandatory and persisted. |
| `GET /api/media/{id}` | Effective owner group plus `can_download=true`. Legacy attachments need a unique stored message-group owner; missing or ambiguous ownership is denied. |
| `GET /api/events?after=...` | An authenticated WebSocket; both durable replay and live group/message/member events are filtered by the effective group set. |
| `/api/local/forwarding`, `/api/local/clients`, `/api/local/clients/{id}`, `/api/local/clients/{id}/revoke`, `POST /api/shutdown` | Loopback administrator only, regardless of a client's group grants or capabilities. |

Every client update increments its revision and closes that key's already connected WebSockets, including after a nickname, group or capability change. Other keys' sockets remain connected. An enabled key reconnects with its current grants; a disabled or revoked key cannot reconnect. A global group-selection change also takes effect in subsequent API checks, replay and live event filtering. Clients should refresh the effective group list and clear any currently displayed group that is no longer permitted.

Changing a client's grants durably fails its unauthorized `queued` sends before they reach the adapter. The bridge rechecks current group/send permission before submitting a send or a new recall, using the internal authenticated owner rather than a caller-provided ID. An action already handed to the adapter is only confirmed and is never automatically resubmitted; read-only `recall_check` recovery may still resolve an existing attempt after revocation. Uploads recheck group, send permission and revision while streaming and before committing metadata; revocation discards the partial file. Downloads recheck group, download permission and revision between bounded chunks and stop the response when access is lost. Attachment metadata in an otherwise readable message does not confer permission to download its bytes.

Before opening SQLite or starting the local adapter, the relay validates the configuration, requires TLS certificate and private-key paths to be configured together, canonicalizes the data directory and takes an exclusive operating-system lock on `<data>/.relay.lock`. The lock file is opened without truncation and contains no credentials; its handle lives for the entire relay process. Different configuration files and relative/symlink aliases cannot start two relays against the same canonical directory. A leftover lock file is harmless after the owning process exits because the operating system releases the lock. The relay then loads/verifies the TLS certificate/key, binds the configured listener and prepares its HTTP or TLS server before opening the store and starting the adapter. Invalid certificates, incomplete TLS settings or an occupied port fail without launching the adapter; non-loopback listeners require TLS.

The Rust Windows adapter implements the supplied local database/media reader, authenticated in-memory SQLite snapshots, WAL processing, media integrity checks and durable confirmation/echo journals. It reuses the verified 4.1.15.13 native sender DLL, links only the C SILK SDK for voice decoding, and invokes a standalone FFmpeg EXE on demand for static WXGF. The adapter directory contains exactly `wechat-adapter.exe`, `WeChatActions.dll`, `WeChatQuote.dll` and `ffmpeg.exe`. The two independent C++ modules have separate tokens, hash directories and selected-group configs; the quote module installs no observation hooks. Their APIs and separate offline CTest executables are documented in `adapters/native/README.md`.

Message-pager signatures cover only `message_<digits>.db` and their `-wal` files. Resource/media databases and `-shm` changes cannot trigger a full message rescan; catalog discovery still finds new/removed databases. At most 128 metadata-only negative entries cache a missing group table or an empty exact query. Entries are bound to the actual snapshot's main/WAL signatures and file identity, plus the group and query parameters; an old connection cannot assign its result to a newer disk signature. Every round still releases decrypted connections. Page authentication, committed-WAL checksums and `quick_check` remain enabled. Pending media retries are independent, normally after 30 seconds. Size/MD5/SHA256 checks precede publication or native staging. The old `adapters/windows` Python implementation is retained for migration history and is excluded from the release runtime.

The macOS relay core and client have independent build scripts, without the Windows adapter/DLLs; they have not been built or validated on the target M4 hardware here. A Mac WeChat adapter with equivalent verified capabilities is not included yet; the client connects to the Windows relay. This condition is reported as not connected, never as successful synchronization. Distribution currently uses relay broadcast, with no client-to-client NAT traversal.

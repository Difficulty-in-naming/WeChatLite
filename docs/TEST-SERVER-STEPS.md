# 本机 Windows 虚拟机测试步骤

这里的“本机测试”指你在本机 Windows 虚拟机使用真实微信与服务端、配合真实客户端的手工测试。单元测试、演示模式和探测脚本是助手的代码验证，不是你的测试。正式服务端在远处，由其他人在其电脑运行，两边结果分别确认。

## 文件已经放在哪里

助手改完代码后负责把新 Windows 适配器和 relay 放进这个原有目录，不需要你下载 ZIP、解压或手动复制 EXE：

```text
\\Mac\Home\Downloads\WeChatLite-构建产物\WeChatLite-Server-测试版
```

对应 macOS 实际目录：

```text
/Volumes/MacData/cal_data/Downloads/WeChatLite-构建产物/WeChatLite-Server-测试版
```

启动文件是这个目录中的 **`启动测试版.bat`**。旧程序和旧说明保留在 **`测试文件备份/`**。当前目录的 `测试构建.json` 记录新文件哈希，启动器会自动核对。

## 你怎么开始

1. 如果原服务端还在运行，从其托盘菜单选择 **“停止服务并退出”**。这一步需要你来做。只关管理窗口可能只是收进托盘。
2. 打开上面的共享目录，双击 **`启动测试版.bat`**。
3. 启动器会显示目录、构建标记和适配器 SHA-256。如果发现旧服务进程或文件不一致，会停止并提示，不会强制结束进程。
4. 在服务端日志确认 `exe=` 指向这个测试目录，且有本次图片兼容标记：

```text
wxgf=start-code-v2 image-download=full-and-mid-v1 image-preview=cdn-footer-v3 media-wait=delayed-clear-v1 inbox-poll=snapshot-v1
```

5. 自动清除提示需要上一轮已交付的新版客户端配合。若已运行该版本，继续使用即可；若仍是更旧的客户端，请亲自正常退出，再双击 macOS 原构建产物目录里的 **`启动测试版客户端.command`**。继续使用原来的配置，客户端目录是 `/Volumes/MacData/cal_data/Downloads/WeChatLite-构建产物`。本轮扫描修正只更新服务端程序。
6. 使用该客户端连接虚拟机服务端，继续使用原来的登录、群和客户端权限，不要重建配置或清除数据。

本次追加 `native-health=split-v1`，将进程、版本和组件初始化失败分别报告；日志与 `测试构建.json` 还会显示内嵌媒体 DLL 的 `native-media-sha256`。GitHub 包会重新编译 DLL，原共享测试版沿用的 DLL 与你提供的 GitHub 包不同；本次对照构建复用你提供包中的同一个媒体 DLL，SHA-256 为 `b6d743801c72b3a24bf7efa658b23d3cf67f01bce7a574548916682a26a15523`。这次若切换到对照构建，需要你先正常退出服务端，再完全退出微信（不是只关主窗口），重新登录微信后启动服务端。远端由对方亲自完成。不要清缓存或重建配置；若仍失败，保留新版具体错误，不能只据 `4.1.15.13` 认定版本不匹配。

启动器复用已有的 `%LOCALAPPDATA%\WeChatLite\WeChatLiteServer\server.json`；测试期间仍会使用该配置指向的数据目录，不是演示实例。助手只更新程序文件，不代你启动或操作真实微信。

## 这次图片问题怎么测

你已在 2026-11-16 确认：本机 Windows 虚拟机使用旧版，接收其他账号发来的图片也正常；本机与远端微信版本相同。因此本机没有复现远端问题，不能再归因为发图账号来源或微信版本不同，也不能用本机旧版正常证明新改动已经修复远端。

本轮重点是关窗后单独一张图片也能独立到达，不靠重新打开微信或再发一条触发。已有的缩略图回退和完整图升级也继续观察。手工操作需要你来做：

1. 在虚拟机中保持微信登录，关闭微信主窗口，确认 `Weixin.exe` 仍运行。
2. 用不同于监听账号的另一个账号发一张新的普通照片到获准使用的群。暂时不要在电脑微信打开该会话或点开大图，以免补齐缓存。
3. 在轻聊客户端看图片能否出现，记录实际等待时间；若先出现较小的缩略图，观察之后是否在同一条消息中变清晰。刚开始下载不应弹出附件等待警告；同一附件等待超过 30 秒才提醒一次。完整附件成功收到后，对应警告应自动消失，其他图片或连接错误的提示不应被误清。仅收到缩略图时，完整图仍在等待，不提前清除警告。
4. 再打开电脑微信主窗口，对比完整图片出现后是否更新原消息，且没有重复消息。

本次还修正了日志明确显示的“下载完成但大小/MD5 与声明不同 → 灰色占位图”问题。CDN 返回的图片若经过重编码，须同次成功回执、实际大小、CDN MD5 和完整解码全部通过才能接收。新版不再发送灰块；启动后会重新读取旧版灰块对应的原图片，取得真实图片后更新原消息。无需删除灰块、清缓存或重建配置。

本机可能直接取得完整图片，因此未必能观察到缩略图回退。远端失败场景仍需对方亲自确认。不要删除任何图片缓存或群消息来制造故障。

完整的手工场景区分如下，按需要记录，不把助手的代码验证结果填到这里：

| 发图者 | 电脑微信窗口 | 验证内容 |
|---|---|---|
| 监听账号本人，用手机发图 | 打开 | 同账号同步 |
| 监听账号本人，用手机发图 | 关闭，进程保留 | 同账号后台同步 |
| 其他群成员 | 打开 | 他人图片接收 |
| 其他群成员 | 关闭，进程保留 | 他人图片后台接收，远端报告的失败场景 |

## 这次改了什么，怎么看结果

本轮追加 `inbox-poll=snapshot-v1`，处理接收时快时慢的一处确定代码缺陷：旧程序可能检测到数据库的新版本，却仍查询上一轮的旧快照，之后等下一次数据库变化才发现消息。现在会在取得本轮版本时清掉对应旧快照，不必靠第二条消息触发。隔离夹具已复现并验证修正；这还不能证明你现场约 10 秒的延迟就是同一原因。

你进一步确认“每次重新打开微信，之前的消息才会发到客户端”，这与上述缺陷相符；修正后的现场结果仍以你的本机手测和对方远端手测分别确认。

另修正 Windows 下载回执的长短路径识别：临时目录里 `RUNNER~1` 一类短路径与缓存的规范长路径可能指向同一文件，旧校验会误拒绝。现在只有两者都指向私有下载目录内同一文件才接受；请求编号、大小、MD5 和完整解码仍需通过。此项修正源于 Windows 构建的离线夹具失败，不代表你的本机手测或远端结果。

这轮手测由你亲自进行：微信关窗、进程仍在时，用另一个账号先发一张新图片，先不要补发第二张或打开电脑微信会话，观察它能否独立到达。若仍慢，保留从发图前到图片收到后的那段服务端日志，再对比第二张和一条普通文字的情况。目前只确认延迟有时出现，尚未确认普通文字是否也受影响。

新增 `[timing] inbox discovered ... kind=image` 表示程序首次发现该图片并入队；同一 `source=` 后面的 `pending`、`item` 是图片处理阶段。日志中的 `at_ms` 是服务端本机时间；慢 `snapshot`、`signature`、`cycle` 会显示本轮读取与处理耗时。这样能分清延迟出现在发现消息之前还是图片处理之后，不需要提供数据库或图片内容。

旧代码只接受原图下载字段 `cdnbigimgurl + hdlength`。没有本地完整图片、原图字段又不全时，即使消息里已有标准图字段，仍会一直等待。新版还接受 `cdnmidimgurl + length`，使用已有原生组件的标准图下载类型。文件大小和 MD5 始终验证；图片重编码产生的差异须有同次成功回执且实际字节符合该回执。

你提供的 `cdn-receipt-v2` 日志确认新图和旧灰块都在重试，但仍报“图片缓存尚未完整写入”。`cdn-footer-v3` 补齐一处代码遗漏：CDN 的 JPEG/PNG 在原始下载字节通过大小和 MD5 校验后，和本地缓存一样去掉结束标记后不超过 32 字节的尾部，再完整解码。你随后提供的日志确认两张 JPEG 都带 24 字节尾部，处理后转换成功；你也确认本机手测前台、后台两张图客户端都已收到。这确认了这两张图的原因与结果，远端正式环境仍需对方确认。

本次追加 `media-wait=delayed-clear-v1`：开始下载时只记录服务端日志，连续等待超过 30 秒后提醒一次。警告绑定同群、同来源的消息，客户端完整接收成功后自动清除；缩略图和未完成的合并消息不算完成。消息仍保留并按原计划重试，非等待的读取错误仍会告警。

完整图还没取得、正在下载或解码失败时，新版会读取同一张图片的 `_t.dat` 缩略图；只有通过解密、完整解码校验的缩略图才显示。预览保存在独立缓存中，不会挡住完整图重试。relay 保留未完成状态，完整图取得后更新原消息，不重复新增消息。若连缩略图也不存在或无法解码，仍需等待真实图片数据，不能凭空恢复。

| 结果或提示 | 含义 |
|---|---|
| 新图片在关窗时显示 | 这张图片、这个来源和本机环境通过；远端结果仍需对方确认 |
| 先显示缩略图，之后同一条消息变清晰 | 缩略图保底与完整图升级通过 |
| 先前的灰块变成真实图片 | 固定指纹识别与旧图片重新读取通过 |
| `微信媒体正在后台下载，大小和 MD5 校验后自动转发` | 已进入后台下载，待完成校验；开始时只记服务端日志，等待超过 30 秒才告警，成功后清除 |
| `微信本地完整图片缓存尚不可用；后台下载参数不可用：…` | 没有可解码缩略图或完整图片，且下载参数不可用；新提示只报告字段有效与否，不含凭据 |
| `微信图片尚未完整下载，只有缩略图时不会转发` | 旧文案；先核对启动目录、哈希和本次标记，不能只看版本号 |
| `微信后台下载组件未就绪：…` 或 `微信 CDN 暂未提供此资源…` | 已找到资源，问题在原生下载组件或 CDN 阶段 |
| `进程或版本校验未通过：pid或版本不匹配（检测到 "4.1.15.13"）` | 旧文案把 PID、版本和组件初始化错误合并，不能据此判定微信版本错误；新版分别报告实际失败项 |
| `本机微信组件初始化失败：native download fingerprint mismatch` | 下载函数或回执观察点的内存指纹不符；若刚升级后台下载组件，先由你正常退出服务端、完全退出微信后重新登录，再启动服务端；远端由对方亲自做。仍失败时保留完整错误，不关闭指纹检查 |
| `本机微信组件进程校验失败：期望 PID …，实际 PID …` 或 `本机微信组件版本校验失败：…` | 分别是组件返回的进程或版本不符，保留这条完整错误；不凭版本显示值推断 PID 或初始化原因 |
| `[media] displaying thumbnail while full picture retries: …` | 已显示缩略图，完整图继续重试；不是空白占位图 |
| `[media] CDN picture normalized: … footer-bytes=…` | CDN 图片的短尾部已去除，图片已通过完整解码 |
| `已校验的微信 CDN 图片无法完整解码（received-bytes=… footer-bytes=… format=… bytes=… …）` | 下载字节已通过校验，卡在图片结束结构或解码；保留这条完整提示即可，无需提供图片文件 |
| `微信图片暂时无法读取，将继续重试：…` | 暂无可解码的真实图片，保留重试，不用灰块冒充完成 |

不要发送完整消息 XML、下载资源编号、AES 密钥、客户端密钥或数据库。普通文字和文件正常、图片单独失败时，不把它写成全部消息无法同步。

## 测完与回退

从测试服务端托盘选择“停止服务并退出”，再运行你原来使用的正式程序。需要回退本机测试文件时，退出服务后取 `测试文件备份/` 中对应时间的文件，按其原相对路径放回；不恢复或改写数据目录。

远端正式环境的替换、启动和手测由对方亲自完成。不要删除测试目录或备份来“清理环境”，也不要把本机共享目录当成远端已更新的证据。

本文的源文件是仓库 `docs/TEST-SERVER-STEPS.md`。共享目录中的 `使用说明.md` 由 `scripts/stage-windows-test.py` 自动同步，避免维护两套不同的流程。
